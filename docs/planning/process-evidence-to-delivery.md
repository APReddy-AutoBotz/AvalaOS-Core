## Delivery implementation boundary

The Delivery PR replaces blank/manual proposal authoring with deterministic proposals from explicit approved requirement lines. Supported lines use a stable requirement identifier (`REQ`, `BR`, `FR`, `NFR` or `AC`) or an explicit normative predicate (`must`, `shall`, `required to` or `needs to`). Headings and descriptive prose do not produce work. Epics summarize actual deliverables rather than document headings; stories separate the concrete deliverable from its source statement. An `AC` line is paired only when it explicitly names the requirement ID or when one requirement makes its same-section association unambiguous. Otherwise a visible human-review task retains the unassigned criterion instead of guessing. Verification tasks retain the exact approved predicates. A document without explicit requirements is blocked with an actionable message instead of producing empty or fabricated work.

The user reviews every proposal, edits its type/title/description/criteria, and selects a subset before publication. Requirement links and the generated proposal role remain immutable. The role distinguishes coordination, implementation, acceptance review and verification even when a user changes a Story to a Task. The server reloads the exact approved artifact, rejects invented or changed source lines, and records a stable origin for every selected proposal without a provider call. Publication still requires the existing current approved version, same-process project binding, current authorization and independent Studio approval. Delivery import remains the final selection and confirmation step. For newly requirement-bound publications only, a selected Epic is a persistent board work item with status, detail and source lineage; Epic-only confirmation is valid. Earlier legacy documents retain their accepted grouping-only Epic behavior.

Board import attaches the approved artifact aggregate, exact approved revision, section links and stable proposal origin to immutable task lineage. Normal task detail provides a keyboard-accessible source-details disclosure with that revision identity, each section and the exact approved quote; it does not grant or route around Studio read authority. Existing task detail and status updates remain persistent. The project-wide unique origin is the stable artifact aggregate plus immutable proposal role and canonically sorted section/requirement identities. Mutable work type is excluded from identity. Generated roles retain their pre-upgrade default-type hash domains (coordination/Epic, implementation/Story and verification/Task), so an unchanged proposal cannot be re-imported after upgrade under a new hash. If a historical proposal was edited to another type, the import boundary checks every allowed historical type domain and fails closed rather than guessing its role or duplicating it. Where a stable `REQ`/`BR`/`FR`/`NFR`/`AC` ID exists, later title or wording edits retain the origin while the historical quote remains immutable proof. It prevents a later revision of the same declared requirement from appearing twice, including after soft deletion or retention, while allowing identical text from an unrelated approved artifact. Publications created before this boundary have no new binding rows and remain importable under the prior approved rules; the binding trigger only acts when a publication has requirement bindings.

Focused verification covers heading rejection, deterministic Epic/Story/Task output, paired acceptance predicates, strict command decoding, adapter lineage, invented-link rollback, atomic publication/replay, link-order invariance, same-artifact/different-artifact origin domains, Epic-only and mixed selective board import, accessible source details and duplicate-origin rejection. The disposable PostgreSQL test is executed separately according to the recorded command result; this document does not promote a static or type check into database proof.

The V2 projection fields are additive to the legacy Delivery response contract. A V1 publication retains its exact assessment id and projects both V2 case/decision fields as null; a native V2 publication has a null V1 assessment id and requires both exact V2 identifiers. Partial or mixed lineage is rejected. This preserves unknown-response replay for historical imports without treating a null field as inferred authority.

Rollback disables publication writes and points the server adapter back only after the old RPC grant is explicitly restored. Existing requirement bindings, publications, generations, imported tasks, approvals and source links remain immutable/readable for forward repair. Dropping bindings or board records is not a rollback path.
