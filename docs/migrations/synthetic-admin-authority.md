## Entry and bootstrap

The `synthetic-admin` Edge endpoint fails closed unless both `SYNTHETIC_ADMIN_ENABLED=true` and one exact `SYNTHETIC_ADMIN_TARGET_FINGERPRINT=sha256:<64 lowercase hex>` are server-set. The browser does not supply or choose the target. The public SQL target row additionally binds that fingerprint, one organization, one workspace, and one explicitly approved operator Auth UUID. `synthetic_admin_assert_target` rechecks active canonical `org.admin` **and** `admin.synthetic.users.manage`, the caller authorization version, actor identity, target scope, and absence of any PR #264 exercise/recovery history before each query or mutation.

Private operator tooling must first independently prove a dedicated target: one approved pre-created Auth UUID and zero profiles, organizations, workspaces, provider configurations, synthetic Admin targets, PR #264 exercises or recovery rows. It may then call the service-role-only `synthetic_admin_bootstrap_operator(p_actor uuid,p_org uuid,p_workspace uuid,p_fingerprint text)`. This uses only the explicit Auth UUID to establish one canonical profile, organization, workspace, organization Admin role, memberships, and current authorization version. Within the **same SQL transaction**, it calls `synthetic_admin_configure_target`, which creates a zero-capability organization member role and four fixed workspace preset roles, grants `admin.synthetic.users.manage` to that specific operator role, enables the target, and sets only that exploratory workspace's process-creation control to enabled, writable, quota 10. The operator must refresh its tenant context after the authorization-version bump. Neither bootstrap function is called by the browser or the synthetic Admin Edge endpoint.

## Admin requests and failure containment

`POST synthetic-admin` accepts exact envelopes with organization/workspace IDs and expected authorization version. Reserve fixes a label and one preset, allocates an Auth UUID and `.invalid` login ID, and enforces a 20-account lifetime cap under the target lock. The Admin can explicitly replay an uncertain reserve with the **same** request ID/key/payload to recover the same row; label search or a new key is not recovery.

Execute receives a 12–72-character temporary password drawn from printable ASCII `0x21–0x7E`, with upper and lower case, digit, and symbol, only in its one HTTPS request body. The UI and server contract share the 72-byte limit enforced by [Supabase Auth password validation](https://github.com/supabase/auth/blob/master/internal/api/password.go); overlong values reject before consuming a provisioning claim. The password is never sent to SQL, stored, hashed, logged, or returned by this subsystem. SQL commits an execution claim before Auth `createUser` runs **once** with the reserved UUID, exact generated login ID, and server-owned reservation/target app metadata. Each Auth request has an eight-second deadline and 32 KiB declared/streamed response cap. A lost, oversized, timed-out, or substituted Auth response reconciles only `getUserById` for that reserved UUID; it never lists Auth users, searches email, generates a second identity, or retries create. SQL independently compares `auth.users` exact UUID/email/app metadata before inserting profile and memberships. A missing or foreign Auth record stays `reconciliation_required`, with no active application membership.

The current [Supabase Auth admin create implementation](https://github.com/supabase/auth/blob/master/internal/api/admin.go) accepts a caller-supplied `id`; its [upstream custom-ID test](https://github.com/supabase/auth/blob/master/internal/api/admin_test.go) exercises that path. This source supports the reserved-ID approach but does not replace exact-target hosted Auth verification. If the target ignores the ID, returned identity is rejected, activation stays unknown, and create is never retried.

Both new service-role mutation RPC adapters (synthetic Admin and process creation) also impose an eight-second deadline across fetch and response consumption and a 32 KiB declared/streamed JSON response cap. They discard raw SQL errors and return only stable domain or unavailable codes. A timeout may follow a committed SQL claim, so the caller must reconcile using the original request binding; it must not manufacture a second account or process with a new idempotency key. The retained general-purpose PostgREST transport is not changed by this narrow correction.

Only the two new creation-access Edge endpoints use the bounded ingress reader: synthetic Admin accepts at most 8 KiB UTF-8 JSON bytes while retaining its existing 2–4096-code-unit raw JSON contract; process creation accepts at most 32 KiB, enough for a valid 4000-code-unit description even when Unicode is escaped. Both enforce an eight-second read deadline, declared and streamed byte caps, strict UTF-8 decoding, and JSON parsing before Auth/SQL effects. Stalled input cancellation is initiated without awaiting a possibly stalled stream finalizer. Invalid input returns only each endpoint's stable invalid-command code. The retained shared HTTP module and other endpoints are unchanged.

Role changes require an active, target-owned synthetic reservation and exact version; they select only the four server-created preset roles. Author can request governed Studio generation/source-package work and manage Delivery packages/items; reviewer can resolve independent Delivery package review; approver can resolve separate Delivery package approval; viewer remains read-only. The canonical `delivery.item.review` action checks `delivery.package.manage`; no nonexistent item-review capability is created. None of these presets receives Admin authority or legacy task execution. Existing default-off feature controls, template/version checks, and provider availability still govern whether a command can actually execute. A replayed command key returns its committed response or rejects changed inputs.

Revoke first disables organization membership, workspace membership, and profile in one SQL transaction, so existing JWTs cannot retain workspace authority. The first exact-ID Auth ban claim is recorded with the original revoke request and an immutable claim receipt. A lost SQL response can be recovered through an authorized `reconcile` with a fresh request ID/key; previously used keys never grant another Auth call. A 30-second lease blocks overlapping Auth calls; two further exact-ID claims are permitted, for at most three ban attempts total. Reconciliation reads only the reserved Auth UUID and checks immutable email/target metadata before any ban. A lost Auth response is followed by an exact-ID read, never a second user creation. `revoked` is committed only after PostgreSQL observes that exact `auth.users.banned_until` is more than 30 seconds in the future. The fenced completion binds the claim token and request ID; a replaced token cannot complete. Both the first `ban_uncertain` transition and the final `revoked` transition increment the account version and write one immutable privileged audit event atomically; duplicate completion returns the existing version without another audit. Confirmation audit correlates the original revoke request and the currently fenced Auth claim request. A lost completion response replays safely, and direct reconciliation can confirm an already visible ban without another Auth call. If ban evidence remains absent after the bounded attempts, the application stays disabled as `ban_uncertain`; private operator repair is required. [Supabase's current ban example](https://supabase.com/docs/reference/javascript/auth-admin-updateuserbyid) uses the same `ban_duration` attribute, and [Supabase's session guidance](https://supabase.com/docs/guides/auth/managing-user-data) confirms a ban does not invalidate existing sessions. The roster exposes only bounded synthetic label, login ID, preset, state, and version to the authorized operator; it never lists all Auth users or exposes passwords, Auth UUIDs, token values, or raw database messages.

## Quality gates and rollback

Focused contract and Edge tests must prove strict extra-field rejection, no Admin preset or self-grant, SQL password exclusion, exactly one Auth create after the durable claim, exact-ID uncertain reconciliation, substituted Auth rejection, database-first revocation, lost pre-ban and post-ban responses, no foreign Auth ban, and default-off zero-effect behavior. PostgreSQL tests must execute the additive migration chain and test empty-target bootstrap, forbidden PR #264 history, quota and ban-claim serialization, wrong actor/tenant/version, role integrity and separation, Auth marker mismatch, replay, cross-workspace denial, revoked subject's next actual process command, stale completion token, absence of synthetic ban evidence, exact confirmed Auth ban, and one audit. Typechecks, Edge typecheck, security/secret hygiene, migration chain, and `git diff --check` are part of the same PR gate. Hosted exploratory target setup, deployment, real Auth ban, and login tests remain `not run` until their separate target/cost approval; local green tests do not establish those results.

`npm run test:creation-access:coverage` separately gates all eleven changed critical TypeScript sources—contracts, clients, service fence, command/endpoint, Auth adapter, **both DB adapters**, and the bounded ingress reader—with real source-mapped Node V8 coverage at 90% lines, 80% branches, and 85% functions. It fails if a mandatory source file is absent from the V8 report, even when the test suite exits green. React UI and SQL are not included in this TypeScript coverage command; their functional and adversarial gates are Playwright and PostgreSQL respectively. Coverage output is task-owned, temporary, and removed after the attempt.

Rollback is read-only: set `SYNTHETIC_ADMIN_ENABLED=false` and set the target row `enabled=false` through the approved private operator path. Keep ledger, audits, roles, and synthetic Auth identities for bounded reconciliation/deprovision rather than dropping tables or deleting histories. Disable the exact exploratory workspace process-creation control separately. Existing PR #264 exercise data and production controls remain untouched.
