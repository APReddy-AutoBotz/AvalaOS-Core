# Creation access UI acceptance and rollback

This file records the UI part of the authorized creation-access repair in PR #264. The existing controlled-human fixture remains fixed; exploratory synthetic accounts require a separately configured synthetic workspace and both current `org.admin` and `admin.synthetic.users.manage` capabilities. Current PR #264 preview accounts have no account-management authority through this UI.

## Acceptance criteria

- Assess V2 says that a new assessment starts from an existing process. Optional V1 import uses an approved compatible source and remains unverified suggestions. The buttons remain governed by their independent V2 create/clone capabilities and V1 source eligibility.
- Application Portfolio sends no projection request when the current tenant context has neither `assess.applications.read` nor `assess.applications.portfolio.read`. It shows a harmless role-unavailable panel instead of a raw database code. Its data, errors, selections, and asynchronous results are fenced by organization, workspace, actor, authorization version, and capability set.
- A portfolio-snapshot-only role can read a tenant-bound snapshot and its waves without receiving detailed inventory. The projection decoder accepts that server-owned subset only when the caller's read scope is snapshot-only, rejects detail rows or wrong-scope snapshots, and continues to reject snapshots for a details-only role.
- Synthetic Admin sends no roster or mutation request absent both current server-projected Admin capabilities. An authorized Admin can reserve one scoped exploratory account, see its generated synthetic login ID, set a strong temporary password exactly once, reconcile an uncertain activation, and change or revoke an active account by server version. Uncertain role/revocation results lock further changes until that account is reconciled. A lost reservation result can recover only by replaying the exact saved reservation envelope; no new identity/key is issued. Roster and command responses reject unrecognized keys or any returned password. The UI does not offer an Admin role preset.
- Every password field clears on submission and on organization, workspace, actor, authorization-version, capability, or session-state change. The roster and prior messages are hidden during a scope transition. The UI never reports account success until the server confirms it.
- The actual application Admin navigation opens Admin Workbench → Users / Roles, not Enterprise Intelligence. Current server Admin capabilities preserve that route across reload even when the legacy user label is Contributor. A supplied empty capability projection overrides a client-side Admin label; the synthetic account panel still requires both of its own server capabilities before requesting a roster.
- A settled `ban_required` or `ban_uncertain` roster row offers only an explicit exact-account Auth-ban reconciliation action. Each operator retry uses a fresh request and operation key; neither pending state is displayed as revoked, and the UI cannot reissue revoke for that row. Only an observed server-confirmed `revoked` result removes the retry action.
- The process modal and Admin panel give keyboard focus to an announced pending status while a request is in flight, move focus to a recoverable alert after a confirmed error, and disable overlapping controls. The process modal traps Tab/Shift+Tab, permits Escape and restores the opener when idle, and cannot be dismissed or duplicated while pending. Desktop and Pixel checks inspect serious/critical Axe violations and document overflow in success, pending, uncertain, and error states.

## Safe rollback

Disable the exploratory synthetic-account feature at the server and hide the new Admin form. Existing reserved, active, uncertain, and revoked records remain durable for read-only reconciliation and an additive correction. Revert only the new UI affordances if needed; do not restore direct browser Auth administration, browser-held service keys, optimistic success, or permission-blind Portfolio reads. Assess V1 scoring and committed V2 cases remain unchanged.
