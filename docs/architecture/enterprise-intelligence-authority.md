## BYOK provider authority

The server owns provider configuration, route eligibility, secret resolution, endpoint selection, allowed roles, model capability, validation freshness, and budget enforcement. Browser state is a projection and never supplies provider authority.

Supported provider identities are `openai`, `azure_openai`, `anthropic`, `gemini`, `groq`, and `openai_compatible`. A route is eligible only when all of the following are true:

- the provider configuration is active and belongs to the current organization and workspace;
- the capability is explicitly allowed;
- the model is in the server-committed model allowlist;
- the opaque secret reference is provider-specific and tenant-bound;
- the secret resolves through the server environment or Vault store, never through a browser payload;
- the provider endpoint is first-party or present in the server endpoint allowlist, with credentials, query strings, fragments, private addresses, and redirects rejected;
- provider validation has a committed `last_validated_at` value;
- the current normalized actor role is permitted by `allowed_roles`; and
- one atomic server-side reservation confirms the configured daily request and monthly token budgets have not been exceeded.

The shared gateway reserves a conservative full-prompt UTF-8 token ceiling before a provider effect. Only one fenced owner may invoke the provider for a receipt/job binding. A sanitized, strictly decoded result is durably staged before actual usage settles the reservation. Response loss, settlement uncertainty, or staging uncertainty retains an `uncertain` reservation for reconciliation and never permits a second provider effect. Deterministic no-effect failures may release the reservation. Provider retirement cleanup covers all six identities, is durable, fenced, retryable, and never returns a raw secret reference.

The governed lifecycle is register metadata, bind a raw key through the dedicated authenticated endpoint or bind an explicitly pre-provisioned server reference, validate, activate, enable or disable capability routes, rotate, and revoke. A writable Vault-compatible backend stores new raw keys; the environment backend is deliberately read-only and accepts only tenant-bound pre-provisioned references. Rotation validates the replacement before the database switches references. Revocation retires the provider/key metadata and disables every associated route across all organization workspaces in one database transaction.

A deterministic replacement-key validation rejection is terminal only after the writable backend confirms removal of the newly written replacement. The prior active key reference and every route remain unchanged. If cleanup fails, the claimed receipt retains a server-only cleanup-required marker and one later fenced owner retries the idempotent removal before recording `VALIDATION_FAILED`; no secret reference enters the response. A pre-provisioned read-only reference has no cleanup effect. Once validation succeeds, any unknown transition outcome, committed transition with a lost response, or receipt-finalization response loss retains the stable planned secret and IDs for reconciliation instead of deleting a possibly committed credential.

Key material is represented in application tables only by an opaque reference containing the organization binding and a truncated one-way fingerprint. Raw keys, access tokens, signed URLs, endpoint credentials, and provider responses containing secrets are not persisted in application tables, command receipts, audit metadata, browser storage, URLs, logs, or evidence. External provider calls are non-atomic effects: the durable command receipt and job state surround them, and failed calls remain failed rather than becoming a success projection.

## Evidence ingestion into Assess

The canonical source is a private object in the server-controlled `source-uploads` bucket under the current tenant/workspace path. This bucket name is one cross-layer constant: an inconsistent source-bucket environment value or allowlist fails before upload intent or Storage I/O, while unrelated export and Studio bucket configuration remains separate. The command accepts bounded text-oriented documents and transcripts: plain text, Markdown, CSV, VTT, SRT, meeting notes, text PDF literals, DOCX text, and the corresponding supported MIME aliases. Individual sources are limited to 12 MiB.

Ingestion records the source and immutable source version in one service-only database transaction after the object is uploaded. The source bytes and extracted text each receive SHA-256 hashes. Extraction is bounded and treats source content as untrusted data. No OCR, audio transcription, remote URL fetch, archive expansion, or instruction execution is part of this vertical.

PR A adds one workspace Source Library projection over those immutable source versions. Assess source sets are independently versioned ordered memberships with explicit semantic roles; changing membership, order, notes, or roles creates a new version under an explicit observed-version precondition. A locked module input bundle binds one exact source-set version and its exact source-version members. Creating a later source-set version stales only unconsumed dependant bundles, extraction runs, and previews; consumed bundles, committed applications, earlier Assess versions, and their evidence remain immutable and readable. The browser may select only exact historical source-set, bundle, job, binding, candidate, preview-batch, and Assess-draft identities projected for the current tenant. A root's current version is never substituted for an explicit historical selector. Bundle hashes, source hashes, provider configuration, route, model, storage coordinates, and extracted content remain server-owned.

Transcript-assisted Assess applies only accepted or edited candidates joined through the exact extraction job and per-source binding for the selected locked bundle version. Candidate Review, counts, previews, and commits use that same lineage and the real persisted preview-batch identity. Each source retains a distinct server-derived anchor. The server previews manual/transcript and cross-source conflicts, requires explicit resolution of every material conflict, and commits at most one new Assess draft version for a batch of at most 100 candidates. Identical proposals collapse to one write while retaining every evidence relationship. Manual-only fields, deterministic scoring inputs/results, approved decisions, and prior versions are never silently overwritten.

AI extraction may propose a field, value, confidence, and server-safe excerpt, but provider output is never source-position authority. After the exact persisted excerpt is grounded in server-extracted text, AvalaOS derives `normalized-text:v1:chars:<start>-<end>`: a zero-based, half-open Unicode code-point range in NFKC, lowercase, whitespace-collapsed text. The first normalized occurrence wins deterministically. Provider locators are ignored, and the server-derived locator is included in the length-framed excerpt-anchor hash and database-canonical provenance hash. Human review is a separate command; edits append an immutable candidate-edit record and may change the value while preserving the exact excerpt and locator source anchor. Candidate approval is not inferred from client state.

Excerpt normalization rejects malformed UTF-16, including unpaired surrogates, before hashing or persistence. Its 480-character bound counts Unicode scalar values rather than UTF-16 code units, so an astral character is retained or removed as one complete value. The exact post-normalization string is shared by locator derivation, hashing, response-loss replay, and persistence.

Candidate values follow the same governed Unicode contract. A provider or reviewer value with malformed UTF-16 is rejected, and the 12,000-character bound counts Unicode scalar values. One exact canonical value is shared by candidate construction, anchor and provenance hashes, staged response-loss recovery, persistence, review/edit lineage, promotion, and replay; no downstream layer applies a different truncation.

Review projection returns that already-governed candidate value intact. A malformed or over-limit database value is omitted fail closed rather than sliced into different reviewer evidence; Accept therefore cannot approve a value different from the value shown.

Promotion requires the user to select a server-projected editable Assess V2 draft and one or more accepted or edited candidates. The browser supplies only those safe selector identities. The server re-derives the current draft version and validates candidate tenant, source version, status, provenance hash, locator, excerpt hash, and current case version. Human-entered fields are not silently overwritten: incompatible values create a reviewable conflict record. Successful field promotions are versioned and retain candidate, source/version, locator, excerpt hash, confidence, reviewer/edit history, and promotion-receipt ancestry. Approved assessments and deterministic scoring are immutable to this path.

Each promoted candidate creates one strict Assess V2 author `EvidenceSubmission` containing exactly `id`, `claimIds`, `sourceType`, `status`, and `validated`. Enterprise fields have no exact governed Assess claim mapping, so `claimIds` is empty; `sourceType` is `document`, `status` is `submitted`, and `validated` is false. Candidate, source/version, locator, excerpt/hash, reviewer/edit, receipt, and case-version ancestry remain in the immutable Enterprise promotion relation, which points to the exact Assess evidence-link ID. The atomic batch response and effect journal retain the ordered evidence-link IDs for response-loss reconciliation. Both superseded single-candidate promotion RPCs are retired from application roles. A dirty pre-release database containing their noncanonical promotion rows fails the forward migration rather than rewriting immutable Assess history or certifying invalid evidence.

Promotion advances the immutable Assess V2 draft by the same ancestry carry-forward law as an ordinary draft save. Every promoted version preserves the prior canonical `source_snapshot`, `imported_facts`, and `agent_necessity` exactly. Enterprise promotion ancestry belongs only in the relational promotion and audit records; it never replaces or appends arbitrary metadata to a native or V1-clone source snapshot.

The forward upgrade begins with a read-only ancestry preflight over every promotion version and its exact predecessor. Missing predecessors or any `source_snapshot`, `imported_facts`, or `agent_necessity` difference raise the stable `ENTERPRISE_PROMOTION_ANCESTRY_HISTORY_REQUIRES_REVIEW` error before the migration performs a mutation; immutable history is never silently repaired.

A stale or changed Studio version is rejected. A cross-workspace request requires current request authority in both the source and target workspaces before receipt creation; source authority alone cannot disclose or mutate the target. The server, not the browser, creates canonical work-item IDs and stores the package, package version, and work items in one service-only transaction.

Delivery and Monitor consume the committed package version and canonical work-item rows. They do not trust browser-provided item IDs, package JSON, or completion counts. Full package items and the minimized baseline-eligibility selector are independently paged with strict server limits and tenant-bound keyset cursors; no unbounded selector or lineage hash reaches the browser. Monitor can establish only a deterministic baseline: the package is approved, every required item is present exactly once, no blocker remains, and all supplied approved item IDs match the canonical item set. The primary Monitor keys presentation state by actor, organization, workspace, and authorization version, but actor identity is never sent as a browser authority claim; the server derives identity and authority from the authenticated request. Live telemetry, task execution, due-date mutation, and completion inference are out of scope.

## Authorization, approval, and persistence

Every mutating command resolves organization membership, workspace membership, normalized organization/workspace roles, and capability grants on the server. An authorization version is captured and rechecked before execution. Capability checks are operation-specific; read permissions do not authorize mutation.

High-impact approval has three distinct people: the creator, an independent reviewer who records a review event against the current resource hash, and the approver who records the final approval. `enterprise_resource_snapshot` is the sole canonical resource-version and resource-hash authority. The Edge layer supplies only tenant-scoped selectors and rationale; a service-only database resolver returns the persisted safe review identity, and the final approval transaction re-resolves the resource, review, reviewer, approver, authorization versions, and separation of duties. A changed resource invalidates the prior review until a new independent review is recorded against the new canonical snapshot.

Mutations use service-role-only database RPCs for the receipt claim and every canonical provider, ingestion, modernization, approval, Delivery, Monitor, and Assemble commit. Claims occur before stable IDs or external effects. Each canonical mutation records its receipt-linked safe effect journal entry in the same database transaction. Repeated requests replay the committed result or stable failure; an in-progress request is not executed twice. First use of one Delivery/Monitor business idempotency key is serialized transactionally before receipt insertion, so concurrent equivalent attempts converge on one canonical receipt and effect while retaining separate transport-attempt evidence. Delivery/Monitor revalidates current actor and any target authority plus structural binding before disclosing a receipt, then returns an exact committed response before mutable workspace-feature or global read-only gates; those gates still run before any new receipt or effect. New tables are additive, forced to RLS, and expose only capability-scoped projections to the browser. Sensitive provider tables and source objects remain server-only.

### Command receipts and runtime controls

The database classifies every supported command before a new receipt is created. Provider lifecycle commands map to `provider`; source creation, extraction, candidate review, and Assess promotion map to `ingestion`; modernization, Studio handoff, Monitor baseline, and non-Assemble approval commands map to `delivery`; blueprint creation and Assemble-blueprint approval commands map to `assemble`. An unknown command or an approval command without an authoritative resource type is rejected.

For a new request, global read-only and the classified area control are checked before the receipt, Storage, provider, or domain effect. An exactly bound, currently authorized Delivery/Monitor committed replay is resolved before those mutable runtime controls, without granting any new effect authority. Disabling one area does not disable another. Each distinct browser action creates a fresh cryptographically random `ei:<operation>:<uuid>` idempotency key and constructs one in-memory payload; a transport retry reuses the exact body, request ID, and key. If both bounded browser-to-Edge transport responses are lost, the browser classifies the outcome as unknown. Delivery/Monitor also returns `COMMAND_OUTCOME_UNKNOWN` when an attempted SQL command's response cannot be read or decoded, its canonical post-execute result cannot be finalized, or its handler-level post-execute current-authority recheck cannot safely complete or disclose the result. Pre-execution authorization failures remain non-disclosing permission denials. Only this command family decodes those structured failed-HTTP outcome signals, and the client maps the legacy `RECEIPT_FINALIZATION_FAILED` response to the same conservative state. Retained non-Delivery/Monitor failed-HTTP responses preserve their established `COMMAND_UNAVAILABLE` boundary. In every unknown-outcome case, the browser disables further mutation in that actor/organization/workspace scope, preserves authored input, and requires an authoritative projection reload before any later action can receive a fresh key. Every read and mutation completion is also bound to its captured actor/organization/workspace scope and monotonic request epoch; a scope change discards the old completion, error, reload, and finalizer writes. If provider authority is stale, the browser retains that original action and calls a narrow server-authoritative recheck with only the operation and safe organization, workspace, provider-configuration, or route selectors. The recheck uses the lifecycle endpoint's exact shared operation/scope predicate: organization authority for register, validate, and activate; exact workspace authority for route changes; combined organization authority for bind, rotate, and revoke; and the established organization-admin equivalence. A transient recheck transport failure retries only the same safe recheck with bounded backoff. Confirmed authority retries the original action with the same payload, request ID, and key while changing only `expectedAuthorizationVersion`. When bind or rotation authority is revoked after a managed write, the browser sends no second mutation or raw key; it retries only a dedicated cleanup call carrying the original action identity and safe selectors until the server confirms cleanup terminalization. Other revoked actions return non-disclosing `PERMISSION_DENIED` without a second mutation request. Raw provider keys remain only in the active invocation, never enter either recheck or cleanup, and are released only after normal terminal completion or confirmed cleanup terminalization. A later user action receives a new key only after the preceding action is terminal or its unknown outcome has been authoritatively reconciled, even when its selectors and payload are identical. The request ID is transport correlation only and is excluded from the canonical request hash. For provider lifecycle commands, `expectedAuthorizationVersion` is also excluded because it is a per-attempt precondition rather than command identity. Receipt identity is organization, workspace, actor, operation, idempotency key, and canonical business-payload hash. The first request ID remains immutable and later IDs are append-only replay evidence. Therefore an exact transport retry and a bounded stale-authority refresh converge on one receipt, while a changed business payload under the same key remains an idempotency conflict.

A receipt is historical execution truth, not current disclosure authority. Before claim and immediately before returning a committed, failed, blocked, claimed, in-progress, reconciled, or newly completed result, the server re-resolves current membership, roles, authorization version, and the operation-specific capability from one canonical command map. It repeats that check immediately before both success and failure finalization and again before the resulting payload is disclosed. Revocation returns a stable non-disclosing `PERMISSION_DENIED` without changing the receipt or revealing its resource; restored authority permits the same actor to replay the original durable result. Provider lifecycle replays apply exact operation-specific organization/workspace authority rather than a generic capability shortcut, while preserving fenced managed-secret cleanup recovery. Current replay/finalization authority is resolved without pinning the historical attempt's authorization version; the original version remains immutable attempt evidence.

Every successful Enterprise or provider result carries an explicit canonical `resourceId`. The command-specific lineage selector must equal it, the receipt `resource_id` must equal it, the same-transaction effect journal must use it, and reconciliation must return it unchanged. `sourceId` and review-event IDs remain lineage metadata and cannot become the canonical receipt resource for promotion or high-impact review. Any identity mismatch fails closed before disclosure and cannot repeat the domain effect.

Receipt completion and failed/blocked finalization are idempotent durable records of an already-started command, not new product actions. Every provider attempt authenticates the actor against the supplied current authorization version, and the locked database transition independently rechecks current authority. A stale version with retained authority leaves the receipt recoverable; a refreshed attempt acquires a newer fence and reuses the same plan and IDs. Confirmed authority removal permits no provider mutation, cleans any uncommitted writable secret, and records one stable non-disclosing blocked result. Claimed receipts carry a bounded lease, persisted execution plan, owner token, monotonic execution fence, and reconciliation count. If a finalization response is lost, the handler reloads the exact terminal receipt. If a domain effect committed first, it reloads and reconciles the receipt from the append-only effect journal without repeating the effect. After lease expiry, one fenced worker may recover with the same plan; stale fences are rejected. `RECEIPT_FINALIZATION_FAILED` is returned only when neither terminal receipt nor authoritative effect evidence can be recovered.

Raw-key bind and rotation persist a server-owned `managed_write` intent before the writable secret backend is called. The intent binds the provider configuration, provider, server-generated secret reference, receipt identity, key-reference ID, safe fingerprint, prior-active-reference hash when applicable, and `planned` write state. The state may advance only from `planned` to `written`; losing that post-write update does not lose cleanup ownership. Recovery resolves the exact planned reference and compares its safe fingerprint before deletion. The raw-key-free revoked-authority recovery RPC is service-only and can claim only the authenticated actor's exact organization/workspace/operation/action/request/provider receipt. It advances to a newer execution fence, then the shared cleanup primitive verifies receipt ownership, provider reference safety, fingerprint equality, active/prior-active protection, and uncommitted state before deletion. Immediately before an external delete, the exact receipt/token/fence renews a 45-second cleanup lease. The Vault delete has a 10-second hard deadline and receives an abort signal; on timeout the worker waits for the aborted request to settle before returning uncertainty. A live owner therefore cannot be reclaimed while its delete is executing. Pre-provisioned references, active or prior-active references, mismatched fingerprints, and references owned by another receipt are never cleanup-managed. Deterministic pre-transition rejection removes the matching managed secret before terminal failure; failed or uncertain cleanup leaves the receipt claimed for one fenced worker and the browser retries only the safe recovery call. Confirmed cleanup records a stable non-disclosing blocked `PERMISSION_DENIED`; response-loss replay returns that terminal fact without another deletion. A deterministic recovery `PERMISSION_DENIED`, including the absence of a cleanup-eligible receipt, is terminal in the browser: the action settles, its in-memory raw key is released, and the original mutation is never resent. Only `COMMAND_IN_PROGRESS`, `PERSISTENCE_UNAVAILABLE`, or a fetch/relay transport uncertainty retries the raw-key-free recovery call. Validation success and uncertain transition or response outcomes retain the secret for reconciliation.

## Rollback and read-only fallback

The first rollback action is to disable affected provider routes and stop new commands. Existing committed evidence, reviews, approvals, packages, and blueprints remain available as read-only projections. The migration is additive; correction uses forward migration or a controlled source-level disablement. No destructive deletion, live endpoint change, credential rotation, deployment action, or hosted rollback is authorized by this document.

The browser workbench is synchronously isolated by authenticated actor, organization, and workspace. A change to any of those values replaces the complete workbench before the new scope's first committed render, clearing raw provider-key input, provider and route forms, private file bytes and metadata, source/candidate/draft/application/decision selectors, blueprint drafts, previews, pending actions, errors, statuses, and child-component state. Async reads and command continuations remain bound to the retired scope and request epoch, so they cannot populate, submit through, clear, or repaint the replacement scope; returning to a prior scope starts a fresh workbench rather than resurrecting browser state. Rollback or read-only fallback must preserve this isolation boundary while disabling mutation and retaining only server-authorized committed projections.
